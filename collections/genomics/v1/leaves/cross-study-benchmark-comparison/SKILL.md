# cross-study-benchmark-comparison

## Summary

Reproduce a published benchmark by re-running a tool-based workflow (here, Staramr with PointFinder on NanoGalaxy de novo assemblies) and directly tallying detected features against the counts reported in an earlier study, explaining any excess as database coverage differences.

## When to use

Use when a target publication reports a numeric result (e.g. number of resistance genes) for named isolates and you need to reproduce the count with your own pipeline and account for discrepancies versus the source study.

## When NOT to use

- The input is raw Nanopore FASTQ reads rather than already-assembled genomes — assemble first with the upstream NanoGalaxy workflow before running Staramr.
- The comparison study used a resistance-screening database with identical scope (no point-mutation screening) and you need strict like-for-like detection counts rather than an explained excess.
- The target study does not report a numeric per-isolate feature count that can be tallied and compared.

## Inputs

- De novo genome assemblies (FASTA) generated by the NanoGalaxy AMR long-read workflow for the isolates also analysed by Li et al.
- Staramr with the PointFinder chromosomal point-mutation database enabled
- Published resistance gene count from Li et al. for the same isolates (reference figure)

## Outputs

- Staramr report with ResFinder hit table (acquired resistance genes)
- Staramr PointFinder hit table (chromosomal resistance-conferring point mutations)
- Tally of total detected resistance genes/point mutations and its comparison against the Li et al. count

## How to apply

Start from the de novo genome assemblies produced by the upstream AMR long-read workflow in NanoGalaxy (Nanopore data analysed in Galaxy). Run Staramr on these assemblies with the PointFinder chromosomal point-mutation database enabled, so both acquired resistance genes (ResFinder hit table) and chromosomal resistance-conferring point mutations (PointFinder hit table) are reported. Parse both Staramr output tables to extract the complete list of detected resistance determinants, then tally the total and compare it with the number reported by Li et al. for the same isolates. Rationale: the NanoGalaxy AMR workflow is expected to detect MORE resistance genes than Li et al. because Staramr additionally screens chromosomal point mutations via PointFinder, so exceeding the published count is the expected, correct outcome rather than an error.

## Related tools

- **Staramr** (Screens the de novo assemblies for acquired resistance genes (ResFinder table) and chromosomal point mutations (PointFinder database) whose combined tally is compared to Li et al.)
- **NanoGalaxy** (Provides the Galaxy-based long-read (Nanopore) workflow that produces the de novo genome assemblies fed into the AMR detection step.) — https://github.com/mmiladi/galaxy-nanopore
- **Galaxy** (User-friendly platform in which the AMR use-case workflow (assembly plus Staramr analysis) is executed without command-line skills.) — https://toolshed.g2.bx.psu.edu/

## Examples

```
docker run -d -p 8080:80 mmiladi/galaxy-nanopore
```

## Evaluation signals

- Staramr runs to completion and produces both the resfinder and pointfinder hit tables for every input assembly.
- The total detected resistance gene/point-mutation count exceeds the count reported by Li et al. for the same isolates.
- The excess in the count can be attributed to PointFinder chromosomal point-mutation detections, not to spurious ResFinder hits.
- All isolates reported by Li et al. are present in the comparison — no isolate is dropped between the two tallies.

## Limitations

- The higher count is a database-coverage effect (Staramr adds PointFinder point mutations), so the result cannot be read as a better assembly or better sensitivity per se.
- Only the most established, widely used tools were integrated into NanoGalaxy, so alternative AMR detection toolchains are not covered by this workflow.
- Only the AMR use-case count comparison is validated; the article notes intensive testing was performed for ONT data specifically.
