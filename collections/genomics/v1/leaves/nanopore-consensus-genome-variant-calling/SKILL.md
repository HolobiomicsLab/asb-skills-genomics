# nanopore-consensus-genome-variant-calling

## Summary

An optional downstream step of the VirDetector nanopore-sequencing pipeline in which structural variants are detected in the assembled viral genomes: Sniffles2 is applied to the consensus genome sequence reconstructed for each sample and the detected variants are written to a per-sample variant record (VCF-style) file.

## When to use

Use when a nanopore virus-surveillance workflow has already reconstructed viral consensus genomes (reference-based or hybrid assembly) and you need to identify structural variants relative to the reference as an optional downstream analysis.

## When NOT to use

- Input is raw FASTQ/FAST5/POD5 nanopore data that has not yet been preprocessed, classified, or assembled into a consensus genome — variant calling in this skill operates on consensus sequences, not reads.
- You only need taxonomic classification or phylogenetic tree inference (maximum likelihood / Bayesian) without structural-variant analysis.
- The workflow is run with the structural-variant step disabled (variant calling is optional; disabling steps leaves samples only preprocessed and trimmed).

## Inputs

- Viral consensus genome sequences per sample (generated by reference-based or hybrid assembly within VirDetector)
- Reference sequence in FASTA format (placed in the resources directory and set via params.ref)

## Outputs

- Per-sample VCF-style variant record file with detected structural variants
- Variant summaries in results.txt alongside other reference-assembly outputs

## How to apply

In VirDetector, structural-variant detection is an optional pipeline step executed alongside the reference-based assembly outputs. For each sample, load the viral consensus genome sequence produced by the reference-based or hybrid assembly step, then run the structural-variant detection tool (Sniffles2) on that consensus sequence to call variants relative to the reference. Write the detected structural variants per sample into a VCF-style variant record file placed in the pipeline's structured output directories, and summarize the detected variants alongside the other reference-assembly outputs in results.txt. Steps are orchestrated through Nextflow (main.nf) and can be enabled or disabled via parameters in nextflow.config; if all steps are disabled, samples are only preprocessed and trimmed, so confirm the variant-calling step parameter is enabled before running.

## Examples

```
nextflow run main.nf
```

## Evaluation signals

- A variant record (VCF-style) file exists for each processed sample.
- Detected variants are summarized alongside the other reference-assembly outputs in results.txt.
- The variant records correspond to consensus genomes reconstructed earlier in the same workflow run, so sample names match the assembly outputs.
- Output files are located in the pipeline's structured output directories as configured via nextflow.config.
- Running the full pipeline (except basecalling) with nextflow run main.nf completes without the variant-calling step aborting.

## Limitations

- Structural-variant detection is optional and depends on a viral consensus genome having been reconstructed first (reference-based or automated hybrid assembly); without an assembly step there is no input for Sniffles2.
- Variant detection operates on assembled genomes relative to a reference sequence, so a reference must be provided (params.ref) for the reference-based assembly route.
- VirDetector was developed and tested under Ubuntu 22.04 LTS; other operating systems require the Docker installation.
